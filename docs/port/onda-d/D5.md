## Tarefa 3: `try/catch` no caminho comum (caso 81)

### Raciocínio sobre o Rust

- `expect_keyword_is(kw)` = `if self.parse_keyword(kw) { Ok(()) } else { self.expected_ref(..) }`. O `parse_keyword` só avança quando casa; o `expected_ref` só monta a mensagem.
- `expect_keywords(&[a, b])` = `for kw { self.expect_keyword_is(kw)?; }`. Consome as keywords que casam e para na primeira que não casa, **sem voltar a posição**. Em `UNNEST(..) WITH x`, o `WITH` fica consumido.
- `ParseKeyword(a) && ParseKeyword(b)` faz exatamente isso: o `&&` não tenta `b` quando `a` falha, e não volta a posição quando `b` falha. `ParseKeywords(a, b)` **não** serve, porque volta a posição (`parse_keywords_indexed`).
- `expect_keyword(VALUE).is_ok()` = `parse_keyword(VALUE)` (o `GetCurrentToken()` devolvido é descartado).
- `expect_token(&t).is_ok()` = `consume_token(&t)`. Os dois comparam `peek_token_ref() == t`; no sucesso, `next_token()` é `advance_token()` + leitura do token atual.
- O `catch (ParserException)` do C# só podia capturar o erro "Expected: ..": nenhuma das funções chamadas lança outra coisa nem mexe em estado no caminho do erro. Os equivalentes são **exatos**, inclusive no consumo parcial.

### Mudança

| Ponto | Rust (mod.rs) | Antes | Depois |
|---|---|---|---|
| `ParseTableFactor`, `UNNEST(..)` | 16676–16679 | `try { ExpectKeywords(WITH, OFFSET); }` | `ParseKeyword(Keyword.WITH) && ParseKeyword(Keyword.OFFSET)` |
| `ParseXmlPassingClause` | 17072–17073 | `if (ParseKeyword(BY)) try { ExpectKeyword(VALUE); }` | `ParseKeyword(Keyword.BY) && ParseKeyword(Keyword.VALUE)` |
| `ParseOptionalColumnOptionGenerated` (3 ramos) | 9812, 9830, 9842 | `try { ExpectToken(LParen); }` | `ConsumeToken(new Token.LParen())` |

Cada ponto ficou com um comentário com o Rust original e a justificativa. São os únicos `.is_ok()`/`Err(_) => false` sobre `expect_*` em `src/parser` e `src/dialect` do sqlparser-rs v0.63.0.

### Testes (`Parser/DiscardedExpectResultTests.cs`)

Os 8 testes foram escritos e rodados **antes** da mudança (passaram com o `try/catch`) e de novo depois, nos três alvos. Os resultados esperados vêm das regras do Rust acima:

- `SELECT * FROM UNNEST(a) WITH` (BigQuery): o `WITH` é consumido e some; a instrução volta como `SELECT * FROM UNNEST(a)`.
- `SELECT * FROM UNNEST(a) WITH x`: o erro aponta para `x` (`Expected: end of statement, found: x at Line: 1, Column: 30`), não para o `WITH`.
- `UNNEST(a) ORDER BY 1`: sem `WITH`, nada é consumido. `UNNEST(a) AS t WITH OFFSET AS o` volta como `.. WITH OFFSET o` (o `Display` do Rust omite o `AS`).
- `XMLTABLE(.. PASSING BY data ..)`: o `BY` é consumido, `by_value` é falso e o resultado é `PASSING data`; `PASSING BY VALUE data` continua com `BY VALUE`.
- `GENERATED ALWAYS AS IDENTITY NOT NULL` e `GENERATED BY DEFAULT AS IDENTITY NOT NULL`: o `NOT` não é consumido pelo teste do `(`. `GENERATED BY DEFAULT AS IDENTITY (START WITH 1)` consome os parênteses. `GENERATED ALWAYS AS x`: o terceiro ramo devolve `None` depois de consumir `ALWAYS AS`, e o erro aponta para `x`.
